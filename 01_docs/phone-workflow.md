# Phone workflow

Features for huxa can be requested, tested and shipped from the phone. Claude Code runs on the server inside tmux as `huxadev`, the Claude app drives it through Remote Control, every feature gets a preview at `https://dev-<topic>.huxa.is`, and `ship <topic>` merges and deploys on the same box. Generated by the phone-dev-workflow kit from `05_scripts/workflow.conf`; the project-specific build and data steps are in `05_scripts/hooks.sh`.

## Start or resume the server

Remote Control runs as a server: one process in tmux, and the Claude app starts as many sessions against it as you like. It starts at boot through a systemd user unit (setup step 8). By hand:

```bash
ssh huxadev@huxa /opt/huxa/05_scripts/remote_control.sh            # start if not running
ssh huxadev@huxa /opt/huxa/05_scripts/remote_control.sh restart
ssh huxadev@huxa /opt/huxa/05_scripts/remote_control.sh status     # also says whether it starts at boot
```

It runs `claude remote-control --spawn=same-dir --remote-control-session-name-prefix huxa` in `/opt/huxa`, so sessions appear in the app as `huxa-...`. The permission mode is not given on the command line; it comes from the committed `.claude/settings.json`: auto mode, `/opt/huxa-dev` in scope, routine git, preview, build and curl commands allowed, force pushes still asking, `deploy.sh` left to auto mode (it runs when you asked for a ship or deploy, never from a worktree), writes to production data, `/etc` and sudo denied. A `--permission-mode` flag would override that file, so do not add one. The Claude app's own mode picker (bottom of the composer, next to the model) also overrides it per session: a session started from the desktop app comes up in whatever the picker says, so keep it on Auto. Sessions started from the phone take auto from the file. Sessions already open when the server restarts end with it; their worktrees and transcripts stay on disk. To watch the server: `ssh huxadev@huxa`, then `tmux attach -t huxa`, detach with Ctrl-b then d.

## Sessions

One integrator session, any number of feature sessions, all in the Claude app under the huxa server.

- **Integrator.** The session pre-created when the server starts. It lives in `/opt/huxa` and only merges and deploys. Keep it; never ask it to implement.
- **Feature sessions.** Start a new session from the app for each feature and open with `/worktree-feature <what you want>`. The skill creates the worktree in `/opt/huxa-dev/<topic>` and the preview. Keep that session for follow-ups until the feature is shipped, then let it go.

## The loop

1. In a new session: `/worktree-feature <what you want>`. The first reply answers the request, lists the shortcuts for the branch after the answer, and ends with **Test it** carrying the preview URL and a **Handover** block. If the app sends the request without the slash command (it happens: the session then receives just the plain text), the session still has to use the skill: the Worktree section of `CLAUDE.md` tells any session asked to build or change something to invoke it itself. A reply that lacks **Test it** and **Handover** means the skill did not run; answer "use the worktree-feature skill" and it will move the change into a worktree.
2. Test on the phone at `https://dev-<topic>.huxa.is`. The preview backend runs on a copy of the production data taken on the first `up`, with the production secrets, so anything changed there stays out of production.
3. Follow up in the same session until it is right. Each change is rebuilt into the preview.
4. In the integrator session: `ship <topic>`, or paste the handover block. It merges into main, runs `05_scripts/deploy.sh`, removes the preview, the worktree and the branch, and tells you to reload huxa.is. One feature at a time. A feature that should not ship is dropped with `drop <topic>`: preview, worktree and branch go, main is untouched.

The rules the sessions follow are the Worktree section of `CLAUDE.md`.

## Housekeeping

```bash
/opt/huxa/05_scripts/server_check.sh                 # everything the workflow relies on, ok or MISSING
/opt/huxa/05_scripts/preview.sh list                 # previews and whether their backend runs
/opt/huxa/05_scripts/preview.sh remove <topic>       # preview, worktree and merged branch
/opt/huxa/05_scripts/preview.sh remove <topic> --force   # the same for an unmerged branch
git -C /opt/huxa worktree list
```

Idle previews cost nothing but disk. After a reboot the Remote Control server and the preview backends start on their own; `preview.sh list` shows a backend that would not. Memory is the limit on parallel sessions: each one takes a few hundred MB plus whatever a build peaks at.

## Deploying from the Mac still works

Push main, then `ssh huxadev@huxa "git -C /opt/huxa pull --ff-only && /opt/huxa/05_scripts/deploy.sh"`, then pull the build commit back. Nothing is built on the Mac.


## Keeping servers aligned

The skills and the kit live in one repo, `dreamspy/claude-skills`, cloned on the Mac and on every server (here in `/home/huxadev/claude-skills`). `~/.claude/skills/` links into the clone, so the skills are always the clone's.

- **Changing a skill or the kit.** Edit it in a clone, commit, push. A session on a server can do this too; the Worktree section of `CLAUDE.md` tells it how.
- **Bringing this server up to date.** Tell the integrator `update kit`. It pulls the clone, renders this project again from the kit, commits and deploys. A change to a skill alone needs only `git -C /home/huxadev/claude-skills pull`.
- **Seeing what lags.** `server_check.sh` reports whether the clone is behind GitHub, has unpushed work, and whether this project was rendered from an older kit than the clone holds.
## Setup, done once

The nine steps that put this workflow on the server, with this project's names. `init.sh` prints the same list.

1. Commit and push. Read `hooks.sh` once more (`build_frontend` is the part that differs per project), review the diff, commit, push main.

2. Prepare the server. Installs nginx, node and tmux, creates `huxadev`, clones the repo, clones the skills repo dreamspy/claude-skills to /home/huxadev/claude-skills and links the skills into ~/.claude/skills, installs dependencies and does a test build.

       ssh huxa 'sudo bash -s' < 05_scripts/server_dev_setup.sh

   On a fresh server it prints the two deploy keys (one per repo) GitHub does not accept yet and stops. Add each where it says, with write access. From the Mac, `gh` can do it:

       gh repo deploy-key add <(ssh huxa 'sudo cat /home/huxadev/.ssh/id_ed25519.pub') -R dreamspy/huxa.is -w -t huxadev@huxa
       gh repo deploy-key add <(ssh huxa 'sudo cat /home/huxadev/.ssh/id_ed25519_skills.pub') -R dreamspy/claude-skills -w -t huxadev@huxa

   Keys added with `gh` are removed if its authorization on GitHub is revoked; keys added on the web page stay.

   Then run the same setup command again.

3. Certificate and DNS. In the Cloudflare dashboard for huxa.is: SSL/TLS, Origin Server, Create Certificate, for the host names huxa.is and *.huxa.is. Save the certificate as `origin.pem` and the private key as `origin.key` on the Mac, then from that folder:

       ssh huxa 'sudo install -d -m 755 /etc/ssl/cloudflare'
       ssh huxa 'sudo sh -c "cat > /etc/ssl/cloudflare/huxa.pem"' < origin.pem
       ssh huxa 'sudo sh -c "umask 077; cat > /etc/ssl/cloudflare/huxa.key; chmod 600 /etc/ssl/cloudflare/huxa.key"' < origin.key

   Delete `origin.key` from the Mac afterwards. Still in Cloudflare: SSL/TLS, Overview, encryption mode Full (strict); DNS, a proxied A record `*` pointing at 54.246.181.20, next to the one for huxa.is itself. Any other certificate that covers both names works the same way.

4. Previews. The preview dir, the nginx site, the secrets file and the systemd user unit for preview backends, and lingering for `huxadev`, which lets its services start at boot. It stops with instructions when the certificate is missing or another site already owns the default server.

       ssh huxa 'sudo bash /opt/huxa/05_scripts/server_preview_setup.sh'

5. Shipping. Installs the root half of a deploy and the one sudo rule `huxadev` gets.

       ssh huxa 'sudo bash /opt/huxa/05_scripts/server_ship_setup.sh'

6. Claude Code on the server. Install it for `huxadev`, copy your instructions (the skills came with step 2), then start it once to trust the folder and log in with `/login` (the Claude account, not an API key), and exit.

       ssh huxadev@huxa 'curl -fsSL https://claude.ai/install.sh | bash && mkdir -p ~/.claude/skills'
       scp ~/.claude/CLAUDE.md huxadev@huxa:.claude/CLAUDE.md
       ssh -t huxadev@huxa 'cd /opt/huxa && ~/.local/bin/claude'

7. First deploy. Builds the site, installs the production nginx site and reloads nginx.

       ssh huxadev@huxa /opt/huxa/05_scripts/deploy.sh

8. Remote Control. Starts the server the Claude app connects to, now and at every boot.

       ssh huxadev@huxa /opt/huxa/05_scripts/remote_control.sh enable

   Then reboot once on purpose (`ssh huxa 'sudo reboot'`), wait a minute and go on with step 9: it shows whether everything came back.

9. Health check. One line per thing the workflow depends on. Every line should say ok; a MISSING line names the step that fixes it.

       ssh huxadev@huxa /opt/huxa/05_scripts/server_check.sh

## Pieces

| Piece | Where |
|---|---|
| Configuration | `05_scripts/workflow.conf` (names, paths, domain), `05_scripts/hooks.sh` (build, seed, bootstrap) |
| Server preparation | `05_scripts/server_dev_setup.sh` (piped to a fresh box), `server_preview_setup.sh`, `server_ship_setup.sh` (root, once each), `server_check.sh` (any time) |
| Previews | `05_scripts/preview.sh`, `04_infrastructure/nginx/huxa-preview.conf`, `04_infrastructure/systemd/huxa-preview@.service` |
| Shipping | `05_scripts/deploy.sh`, `04_infrastructure/sudo/huxa-activate` (root half), `04_infrastructure/sudo/huxadev` (sudoers) |
| Permissions for sessions | `.claude/settings.json`, committed; read by every session spawned in `/opt/huxa` |
| Secrets for previews | `/etc/huxa/preview.env`, copied from production by `server_preview_setup.sh` |
